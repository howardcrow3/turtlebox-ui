Turtlebox UX framework v0.1 draft for review
Plan for review · nothing is built yet

One Turtlebox look, starting with a CeeVee redesign

CeeVee moves to a chat-first desktop layout. Job types, which define what CeeVee searches for, get their own place in the sidebar. Settings leave the main navigation and live behind an account menu at the bottom left, which opens a modal with tabs down the left side. Sign in with Google becomes the first thing a new user sees. Type is all sans-serif, smaller and tighter, and controls such as toggles replace most checkboxes and long forms. The same tokens and components become the shared Turtlebox framework, with Golden as the second app to adopt it.

Every mockup below is live. Open the account menu, switch settings tabs, flip the toggles, and try the Light and Dark preview above.

What changes from the current design

The current Turtlebox system was written for the marketing site. These rows replace the parts that conflict with the new direction. Everything else, including the warm neutrals, the single gold accent and the plain-spoken voice, stays.

Job types

A job type is a saved search with its own rules

Each job type holds the criteria CeeVee searches with, where it looks, and how much it may do on its own for that type. A user might have "Design leadership" in Denver, "Product management" remote only, and a short-term "Remote contract" type. Jobs and applications are tracked by job type and by company, so the Jobs page can show everything or one type.

Lists, density and how they work with chat

The first draft sized controls like a marketing site, and every result was a card. That cannot hold 143 jobs or 40 applications. Use the Jobs list and Applications views in the first mockup to see the answer below.

ElementFirst draftNow
Button32px tall, 13px text26px tall, 12.5px text. Small is 22px and is used inside rows and cards.
Select, toggle, chip30px, 18px, 24px26px, 15px, 22px
Table rowCards, about 52px each30px, one line. Header 26px.
Row actionsText buttons on every rowTwo 22px icon buttons that appear on hover or selection. Everything else goes through selection and the bulk bar.
Navigation item30px28px. Sub-items 26px.

Jobs: a table, not cards

One row per job: title, company, job type, pay, posted, match. Filters sit above as removable chips. Sort and group by job type or company. Rows load as you scroll, so 143 or 5,000 jobs cost the same. New jobs since the last visit are the default filter, so the list opens short.

Applications: a board and a table

Board by default, with a column per stage and compact cards. Each column shows its top cards and "+N more". Table view takes over when there are many. Stale applications are flagged with a gold outline and a plain-words reason, such as "10d, no reply".

Selection and bulk actions

Select rows with the checkbox, the keyboard (x) or shift-click. A bulk bar appears with Draft applications, Save, Dismiss. This keeps the buttons per row to icons and keeps the primary action in one place.

Detail on demand

Clicking a row opens the job or application in a side panel with the posting, tailored resume, letter and history. The list stays visible behind it, so moving down the list is one keystroke.

How chat and lists work together

  • In chat, results are a short list, not a wall. CeeVee shows at most three to five compact rows, then "Show all in Jobs", which opens the full table with the same filters applied.
  • On every list page, chat is a side panel. "Ask CeeVee" opens a panel that knows what you are looking at: the current filters and the selected rows. It can change the list ("only pay above $170k, sorted by match"), act on the selection ("draft applications for these"), or answer questions about it. It hides with one click.
  • Chat changes are visible and reversible. Anything CeeVee does to a list appears as filter chips you can remove, so you always see why a list looks the way it does.
  • Approvals stay in one place. An approval card in chat is a compact two-line item with small buttons. The same items also collect under Inbox, filtered to "Needs you", so nothing depends on scrolling a conversation.
Mockup 1, continued

Chat and forms edit the same thing

The answer is a three-pane workspace for everyday work, and modals for focused tasks. Open "Job types" and "New job type" in the first mockup. Both ways in change one underlying job type, so a user never has to pick between talking and filling in a form.

Three panes

Navigation on the left, the work surface in the middle (a list, a form or a detail view), and chat on the right. The chat pane knows what the middle pane shows. It is on by default for Job types, Jobs and Applications and can be hidden. On the Chat page itself the middle pane is the conversation, and the right pane opens only when chat produces something to edit.

Chat fills the form

When chat changes a job type, the changed fields in the form get a gold dot, show the old value, and the bar says how many changes are unsaved. Accept all, Undo, or edit any field by hand. Nothing is saved until the user accepts, which matches the approval model.

The form steers chat

Edits made by hand are visible to chat. The context chip at the bottom of the chat pane says what it is looking at, so "make it hybrid" refers to the open job type and the selected rows, not to a guess.

Modals for focused tasks

Creating a job type opens a two-column modal. Chat on the left asks what the user wants, and a live draft form on the right fills in as it understands. Either side works alone. Review of an application draft uses the same shape: the document in one column and chat in the other.

Charts and dashboards with a movable time axis

Time controls

One bar above the content sets the range for everything below. Grain buttons change the bucket size and keep the same moment in view. Back and forward move by half a window. Plus and minus change how many periods show. Left and right arrow keys work on the bar and on the overview. Today jumps to the latest period.

Chart types in the kit

Grouped columns, line and area with a crosshair, bands for projections, horizontal bars with the value at the tip, sparklines in stat tiles, and an overview with a draggable window. Every chart has a hover readout that lists all series at that point, and the main ones have a Table view.

Color

Data colors are separate from the gold UI accent. Series use blue, orange and aqua, in that order, validated for color-blind readers and for contrast against both light and dark surfaces. Light-mode orange and aqua are below 3:1 on the surface, so every chart also has a legend, a hover readout and a table view. Text is never colored by a series.

What is still open

Real data scale (tens of thousands of transactions) needs aggregation in the Rust core, not in the browser. Pan by dragging the main chart, a pinch or wheel zoom, and comparing two time ranges are not drawn yet. Say which of those Golden needs first.

Themes

Light and dark, both first class

Every component is written against role tokens, so a theme is only a different set of values. The default follows the computer's setting. Users can force Light or Dark under Settings, General, Theme, and the page-wide switch at the top of this page does the same here. Below, the same screen is rendered in both themes at once.

Dark is warm charcoal, not black, so gold stays the only accent. Text pairs hold 4.5:1 in both themes. Gold is a fill, never text, and the Google button switches to Google's own dark variant.

Mockup 2

Settings is a modal with tabs on the left

Everything you set once or change occasionally moves here: profile and resume, automation levels, models, connected accounts, document storage, notifications, license and updates. Nothing in the modal is needed for daily work. Search criteria are not here, because they change as the search changes: they live under Job types in the sidebar. Escape closes it, and each tab has a stable name so the account menu can open it directly.

Mockup 3

Sign in with Google

The button follows Google's published pill style (white or dark, G mark, 40px or taller) so users recognise it. It sits where the user's eye lands first, above any other choice. Google sign-in stays optional, as already decided. Skipping it leaves local mode fully working, with email through an app password. The explainer step says in plain words what Gmail access is for, matching the Google verification submission.

  • The same button appears in the Accounts tab and inline in chat when CeeVee needs Gmail ("Connect Google so I can see replies").
  • The browser handoff uses the system browser with a loopback redirect. The app window shows a waiting state with Cancel, never an embedded login page.
  • The account menu shows the Google avatar and email once signed in. Signed out, it shows a Sign in row at the top of the menu.

Plan

How CeeVee moves over

Small pull requests against main, each one passing tests and evals before merge. CeeVee's UI is SvelteKit, so the first component implementation is Svelte on top of plain CSS variables. The CSS and tokens are framework-neutral, so another app can use them without Svelte.

  1. Tokens and base CSS. Replace fonts and sizes, add the new roles, keep old role names working. No visible layout change except type and corners.
  2. Core controls. Button, Toggle, Segmented, Select, TextField, Chip, SettingRow, with unit tests and a keyboard and contrast check.
  3. App shell. Sidebar, account menu and the new navigation. Existing pages keep working inside it.
  4. Settings modal. Move the existing settings page into tabs, one tab at a time, then delete the page.
  5. Job types. Sidebar item, list and criteria editor on top of the existing categories data, then filter the Jobs page by type.
  6. Three-pane workspace and chat handoff. Chat pane that reads the open page, the marked-changes pattern on forms, and the two-column modal for creating a job type.
  7. Lists. DataTable with filters, selection and bulk bar, applied to Jobs first, then Applications with the board view and the chat panel.
  8. Chat home. Home view, composer, thread, approval cards wired to the existing approvals queue and profile-update confirmations.
  9. Sign in with Google. Welcome step, explainer, waiting state and the Accounts tab, on the existing OAuth plumbing.
  10. Retire the old header and pages that the chat and modal replace. Jobs, Applications, Inbox, Documents and Network stay as full pages, restyled.

Where the shared framework should live

Once you approve the design, the framework needs a home every app can pull from. Three options:

OptionProsCons
A. New repo, turtlebox-ui (recommended)Single source for tokens, CSS and components. Apps pin a version. A browsable preview page and the Design System artifact can be generated from it. Does not tie to the website repo.One more repo to maintain. Needs a small release step.
B. Folder in highturtle (turtlebox/design-system/)Where the current system already lives. Nothing new to create.Mixes UI code with the site and billing backend. Desktop apps would depend on the whole repo.
C. Existing shared repo (box-common)Already a shared place if its purpose fits.I have not read it, so I cannot say whether it fits. Golden would consume whichever option you pick.

With option A the layout would be tokens/ (JSON source, generated CSS), css/ (framework-neutral component styles), svelte/ (components for CeeVee), docs/ (usage and the preview page), and a version tag per release. CeeVee consumes it as a pinned git dependency at first, and as a package later if there are more than two apps.
